IntroductionIntroduction

Multimedia communication is the exchange of multimedia data (text, image, audio, video) between systems over a network, often with real-time requirements, in a distributed environment.

Why it is harder than data communication

Aspect Traditional data Multimedia
Volume Small Very large (video of several Mbit/s)
Time Not critical Delay and jitter critical for continuous media
Loss Not tolerated (retransmit) Some loss tolerated (audio, video)
Pattern Bursty, point to point Continuous and bursty, often multicast
Synchronisation None Between streams (lip sync)
Source note: Introduction

IntroductionCommunication patterns

  • Point to point (unicast), point to multipoint (multicast, broadcast), multipoint to multipoint (conferencing).
  • Interactive (conference, delay about 150 ms or less one way) and retrieval (video on demand, start-up delay tolerated).
Source note: Introduction

IntroductionLayered view

The textbook divides a multimedia communication system into an application subsystem and a transport subsystem on top of the network, with QoS and resource management across all of them.

Source note: Introduction

IntroductionNetwork requirements

  1. High and guaranteed bandwidth.
  2. Bounded end-to-end delay and low jitter.
  3. Multicast support.
  4. Reliability adjusted to the medium (some errors acceptable).
  5. QoS guarantees and resource reservation.
Source note: Introduction

Application SubsystemApplication Subsystem

The application subsystem contains the services that make collaborative and distributed multimedia applications possible. It uses the transport subsystem below it.

Collaborative computing

Computer-supported cooperative work (CSCW): people at different places work together with shared multimedia tools: video conferencing, shared whiteboard, shared applications, shared documents.

  • Synchronous (same time, for example a video conference) and asynchronous (different times, for example multimedia mail).
  • Shared workspace: one application's output is shown at several sites. Shared execution environment: each site runs the same application on the same data.
Source note: Application Subsystem

Application SubsystemSession management

A session is the period during which the participants and their media connections exist. Session management covers:

Function Meaning
Session setup and teardown Create and end the session; announce it (session directory)
Membership Who joins or leaves; invitation, rendezvous (finding the partners)
Media management Which streams (audio, video, whiteboard) each participant uses; configuration
Floor (conference) control Who may speak or control the shared tool now: floor control policies (chair-controlled, first come first served)
QoS negotiation Agree on the quality each stream uses
Source note: Application Subsystem

Application SubsystemArchitectures

  • Centralised: a multipoint control unit (MCU) receives all streams and mixes or switches them.
  • Distributed: every participant sends to all others (multicast), no central mixer.

Multimedia mail and messaging

Messages carrying text, images, audio and video. Large messages need storage; MIME describes the media types in the body.

Source note: Application Subsystem

Transport Subsystem

Transport SubsystemIn plain words

The idea

RTP carries media with sequence numbers and timestamps; RTCP reports quality. They run over UDP because late data is useless, so waiting for retransmission is pointless.

Real-life picture

Live streaming: a lost frame is skipped, not resent.

Remember it

UDP + RTP for media, RTCP for feedback, TCP is a poor fit for real time.

Say: RTP carries media with sequence numbers and timestamps; RTCP reports quality. They run over UDP because late data is useless, so waiting for retransmission is pointless.

Transport SubsystemRequirements on a multimedia transport subsystem

  1. High throughput for large continuous streams.
  2. Bounded delay and small jitter (about 150 ms end-to-end for interactive audio and video).
  3. QoS support: applications can specify and get guaranteed service.
  4. Multicast for group communication.
  5. Suitable error handling: continuous media prefer timeliness over perfect reliability.
  6. Synchronisation support between streams (time stamps).
  7. Efficient processing: low protocol overhead, no extra copying.
Source note: Transport Subsystem

Transport SubsystemWhy TCP is unsuitable and UDP is not enough

Protocol For multimedia
TCP Retransmission and congestion control add delay and jitter; no multicast
UDP Fast, supports multicast, but no ordering, timing or feedback
Source note: Transport Subsystem

Transport SubsystemReal-time protocols on the Internet

Protocol Role
RTP (Real-time Transport Protocol) Runs over UDP; carries payload type, sequence number and time stamp so the receiver can reorder, detect loss and play out at the right time
RTCP (RTP Control Protocol) Sends feedback on quality (loss, jitter), source identification and helps synchronise audio and video
RTSP (Real-Time Streaming Protocol) Remote control of streams (play, pause, seek)
RSVP (Resource Reservation Protocol) Reserves network resources along a path
ST-II Stream protocol with resource reservation and multicast
Source note: Transport Subsystem

Real-time protocols on the InternetPlayout buffer

The receiver delays playback by a small playout delay held in a buffer, absorbing jitter. A larger buffer removes more jitter but increases delay.

Playout delay

If packets arrive between 40 and 90 ms after sending, jitter is 50 ms. A playout delay of 90 ms from the send time makes every packet available when needed; the cost is 90 ms of latency.

Source note: Transport Subsystem

Transport SubsystemError control

  • ARQ (retransmission): reliable but adds delay; used only for data and when time allows.
  • FEC (forward error correction): redundancy lets the receiver repair loss without retransmission.
  • Concealment: repeat or interpolate missing audio or video parts.

Networks

Ethernet (shared, no guarantee), FDDI, ATM (cells of 53 bytes, built-in QoS classes), ISDN (64 kbit/s channels), and today IP networks with DiffServ or IntServ.

Source note: Transport Subsystem

Transport SubsystemCheckpoint

Check yourself

Why is RTP used over UDP rather than TCP?

UDP avoids retransmission delay and supports multicast; RTP adds sequence numbers and time stamps for ordering and playout.

Check yourself

What does a playout buffer do?

Absorbs delay variation (jitter) so media plays smoothly, at the cost of extra delay.

QoS and Resource ManagementIn plain words

The idea

Quality of Service (QoS) is a set of promises about performance: how much data, how fast and how steadily. Applications ask for it and the system agrees or refuses.

QoS and Resource ManagementQoS and Resource Management

Quality of Service (QoS) is the set of parameters describing how well a service is delivered, and the guarantee that it will be delivered at that level.

QoS layers

Layer Example parameters
User (perceptual) Picture quality (good, fair), sound quality (CD, phone)
Application Frame rate, resolution, colour depth, compression method
System CPU time, memory, buffers
Network Throughput, delay, jitter, loss rate
Source note: QoS and Resource Management

QoS and Resource ManagementNetwork QoS parameters

Parameter Meaning
Throughput (bandwidth) Data rate needed (for example 1.5 Mbit/s for MPEG-1 video)
Delay (latency) End-to-end time; ≤ 150 ms for interactive audio
Jitter Variation of delay; audio can tolerate about 10 ms
Loss / error rate Fraction lost; audio and video tolerate small loss

Guarantee classes

Class Meaning
Guaranteed (deterministic) Always met; worst-case reservation
Predictive / statistical Met with a given probability
Best effort No guarantee

Source note: QoS and Resource Management

QoS and Resource ManagementQoS management steps (2/2)

  1. Specification: the user states the QoS (for example flow specification: rate, delay, loss).
  2. Negotiation: user, application and network agree on achievable values.
  3. Admission control: accept only if existing guarantees stay safe.
  4. Resource reservation: reserve bandwidth, CPU and buffers (RSVP).
  5. Monitoring and enforcement (policing): check that the sender keeps to its specification and the network keeps its promise.
  6. Adaptation: if QoS drops, the application lowers its rate (for example fewer frames) or renegotiates.
Source note: QoS and Resource Management

QoS and Resource ManagementTraffic shaping

To keep the traffic within the agreed specification, the sender (or network) shapes it.

  • Leaky bucket: data enters a bucket and leaves at a constant rate, smoothing bursts; excess overflows (dropped).
  • Token bucket: tokens arrive at rate r into a bucket of size b; a packet needs a token. Allows bursts up to b while keeping the average rate r.
Token bucket

r = 100 packets/s, b = 20 tokens. After a quiet period the bucket is full; a burst of 20 packets can go at once, then the sender is limited to 100 packets/s. In any interval t the maximum is about b + r·t (compare the LBAP in Unit 7).

Source note: QoS and Resource Management

QoS and Resource ManagementResource management in the communication system

  • Resources: link bandwidth, router/switch buffers, CPU of end systems.
  • The end-to-end guarantee needs resource reservation at every hop plus scheduling (for example weighted fair queuing) in routers.
  • Scalability and cost are the practical difficulties; many networks use DiffServ (classes) instead of per-flow reservation.
Exam tip

A five-mark "QoS" answer: define QoS, list throughput, delay, jitter, loss, the three guarantee classes and the negotiation → admission → reservation → monitoring chain.

Source note: QoS and Resource Management

Check yourself

Differentiate leaky bucket and token bucket.

Leaky bucket outputs at a fixed rate (no bursts out); token bucket allows bursts up to the bucket size while keeping an average rate.

What is admission control in a network?

A decision whether a new flow can be accepted without violating guarantees already given.

QoS and Resource ManagementTraffic shaping with a token bucket

A flow conforms if its cumulative traffic never exceeds b + r·t: bursts up to b are allowed, the long-term rate is limited to r.

QoS and Resource ManagementJitter and the playout buffer

Packets leave at a steady rate but arrive unevenly. Holding them in a buffer and playing at a fixed later time restores the steady rhythm, at the cost of extra delay.
