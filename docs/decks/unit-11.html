Abstraction Levels and Libraries

Unit 11 · topic 1 of 4

Abstraction Levels and LibrariesThe state of the art (introduction)

  • Most commercially available multimedia applications are written in procedure-oriented languages.
  • Application code is highly dependent on the hardware, so changing a multimedia device often needs re-implementation.
  • Operating system extensions try to solve this, and there are different ways to access and represent multimedia data.
Source note: Abstraction Levels and Libraries

Abstraction Levels and LibrariesAbstraction levels (1/3)

Abstraction levels in programming are different approaches with a varying degree of detail for representing, accessing and manipulating data.

Source note: Abstraction Levels and Libraries

Abstraction Levels and LibrariesAbstraction levels (2/3)

Level (low to high) Idea
Device A component for continuous media can exist separately in the computer. It is not part of the OS but is directly accessible to every component and application
Library The simplest level; functions for controlling the hardware with specific device-access operations
System software Processing of continuous data becomes part of the OS; needs schedulers such as rate monotonic or earliest deadline first; a device driver embedded in the OS simplifies access and scheduling
Toolkit A simpler programming-environment approach to control audio and video; hides process structures
Higher programming language The language contains abstractions of multimedia data (a higher procedural language)
Object-oriented approach First introduced to reduce complexity; gives a class hierarchy for manipulating multimedia
Source note: Abstraction Levels and Libraries

Abstraction Levels and LibrariesAbstraction levels (3/3)

Higher in the diagram means more abstraction, more hardware independence, easier programming, usually at some cost in speed.

Source note: Abstraction Levels and Libraries

Abstraction Levels and LibrariesLibraries (1/2)

  • Libraries contain sets of functions used to process continuous media. They are supplied with the corresponding hardware.
  • Some are extensions of the GUI; others are control instructions passed as control blocks to the drivers.
  • Very useful at the OS level. Because the OS gives insufficient support for continuous data and there is no integration into the programming environment, a variety of interfaces and libraries will always exist.
  • Libraries differ in their degree of abstraction, and there is no agreement on which functions are best for different drivers.
Source note: Abstraction Levels and Libraries

System Software

Unit 11 · topic 2 of 4

System SoftwareSystem Software

Instead of a separate library per device, device access becomes part of the operating system. Continuous-data processing needs real-time schedulers (see Unit 7).

Example: the Nemo system

Nemo consists of the Nemo Trusted Supervisor Call (NTSC) running in supervisor mode and three domains in user mode: system, device drivers and application.

Not the TV standard

NTSC here means Nemo Trusted Supervisor Call. It has nothing to do with the NTSC television standard of Unit 4.

Source note: System Software

System SoftwareExample: the Nemo system (2/2)

  • The NTSC code implements the functions needed by user-mode processes and supports three kinds of processes:
    • System processes: implement most of the OS services.
    • Device processes: like system processes but attached to device interrupt stubs that run in supervisor mode.
    • Application processes: contain user programs.
  • NTSC calls are in two classes: calls only a privileged system process (for example the kernel) may execute, and calls any process may execute.
  • NTSC provides the interface between a multimedia hardware device and its driver process, so even a device with only a low-level hardware interface can be used.
  • Processes talk through IPC (inter-process communication), built on low-level events and, if needed, shared memory.
Source note: System Software

System SoftwareData as time capsules

A time capsule is an abstraction related to file systems: a file extension for storing, modifying and accessing continuous media. Each LDU carries, besides its data type and value, its valid life span. The concept is used more for video than for audio.

Source note: System Software

System SoftwareData as streams

A stream is the continuous flow of audio and video data. It is established between a source and a sink before the flow starts. Operations on a stream: play, fast forward, rewind, stop.

In Microsoft Windows the Media Control Interface (MCI) gives access to continuous media streams and their devices.

Toolkits and Higher Programming Languages

Unit 11 · topic 3 of 4

Toolkits and Higher Programming LanguagesToolkits

Toolkits control audio and video processing in a programming environment. They represent interfaces at the system-software level, can be embedded into programming languages or object-oriented environments, and are used to:

  • abstract from the physical layer;
  • give a uniform interface for all different continuous-media devices;
  • introduce the client-server paradigm;
  • hide process structures.

It would be valuable to have the same toolkit on all platforms, but experience shows this remains a wish and would reduce performance.

Source note: Toolkits and Higher Programming Languages

Toolkits and Higher Programming LanguagesHigher programming languages

  • In a higher (high-level) language (HLL), processing of continuous media is done by groups of similarly built functions.
  • The calls are mostly hardware and driver independent.
  • Programs either access multimedia data structures directly or communicate with the active processes of the real-time environment; devices are controlled through drivers.

Media can be seen in three ways inside a language.

Source note: Toolkits and Higher Programming Languages

Higher programming languages1. Media as types

  • Audio and video are data types, just as character is the type for text (the smallest addressable element).
  • A program can copy, compare, delete, read, store and display them, and use them in other data structures.
  • Example (OCCAM-2, derived from Communicating Sequential Processes for transputers): two audio LDUs from two microphones are read in parallel and mixed:
a, b REAL;
ldu.left1, ldu.left2, ldu.left_mixed AUDIO_LDU;
WHILE
  COBEGIN
    PROCESS_1  Input(micro1, ldu.left1)
    PROCESS_2  Input(micro2, ldu.left2)
  ldu.left_mixed := a * ldu.left1 + b * ldu.left2;
END WHILE
Source note: Toolkits and Higher Programming Languages

Higher programming languages2. Media as files

A continuous stream is treated as a file: open associates a device with a file name and returns a file descriptor; read, mix, activate, deactivate and close follow.

file_h1 = open(MICROPHONE_1, ...)
file_h2 = open(MICROPHONE_2, ...)
file_h3 = open(SPEAKER, ...)
read(file_h1); read(file_h2)
mix(file_h3, file_h1, file_h2)
activate(file_h1, file_h2, file_h3)
...
deactivate(...);  rc1 = close(file_h1) ...

Difference from discrete files: continuous read/write keep assigning new values continuously to a variable bound to one read, whereas for discrete data each read call fetches the next value.

Source note: Toolkits and Higher Programming Languages

Higher programming languages3. Media as processes

Processing continuous data is time dependent: the life span of a process equals the life span of a connection between source and destination (local or remote). The process is created, reserves the devices at creation, and its actions are controlled by IPC messages:

PROCESS cont_process_a;
  on_message_do
    set_volume ...
    set_loudness ...
pid = create(cont_process_a)
send(pid, set_volume, 3)
send(pid, set_loudness)
Source note: Toolkits and Higher Programming Languages

Toolkits and Higher Programming LanguagesLanguage requirements (1/2)

  • The HLL must support parallel processing; the number of processes is known at compile time, and processes can also be defined dynamically at run time.
  • The IPC mechanism must transmit audio and video in time (they have a limited life span). It must:
    • understand a priori or implicitly specified time requirements;
    • transmit the data according to those requirements;
    • start processing the received data on time.
  • Language: the authors see no demand for a new dedicated language. Replacing a language is difficult because cooperation between the real-time environment and other programs needs semantic changes. A language extension is proposed, a simple language meeting the requirements; examples: OCCAM-2, Ada, parallel C variants for transputers.
Source note: Toolkits and Higher Programming Languages

Toolkits and Higher Programming LanguagesLanguage requirements (2/2)

View Media is a Typical operations
Types Data type (like char) Assign, copy, mix with operators
Files File open, read, write, activate, close
Processes Process (life span = connection) create, send messages

Object-Oriented ApproachesObject-Oriented Approaches

The object-oriented (OO) approach was introduced to reduce complexity and to enable reuse of software components. Its basic ideas are data encapsulation and inheritance, with classes, objects and methods instead of functions and data structures.

Source note: Object-Oriented Approaches

Object-Oriented ApproachesBasic concepts

Concept Meaning Example
Class A collection of objects with the same properties and behaviour; a blueprint. Creating an object is instantiation Class Circle with attributes x-coord, y-coord, radius a and methods findArea(), findCircumference(), scale()
Object A real-world element with identity, state and behaviour; physical (a car) or conceptual (a project) A particular circle
Inheritance A subclass acquires attributes and methods of a parent (super)class: an "is-a" relation, giving code reuse; the subclass may add or modify Cow is a Mammal
Polymorphism Same operation name, different implementation by object; common external interface with different internals findArea() in Circle and Square
Source note: Object-Oriented Approaches

Multimedia classes (ways to build the hierarchy)Application-specific metaphors as classes

A metaphor is a set of UI visuals, actions and procedures exploiting what users already know from other domains. A class hierarchy designed for one application is simple, but the reuse advantage is lost.

Application-generic metaphors as classes

Combine functions common to all applications into classes; an application is defined by binding these classes, and application-specific subclasses inherit the general methods.

Source note: Object-Oriented Approaches

Multimedia classes (ways to build the hierarchy)Devices as classes

  • Objects reflect the physical view: each device is an object representing its behaviour and interface.
  • Similar methods such as start, stop, seek are defined device-independently.
  • Some units handle several media together (a computer-controlled VCR or laser disc player binds video and audio).
  • Abstract devices such as camera and monitor can be defined.
  • Defining a general interface for many audio/video units is a difficult design task.
Source note: Object-Oriented Approaches

Multimedia classes (ways to build the hierarchy)Processing units as classes

Source objects, destination objects and combined source-destination objects that process continuous data between them. Like a "Lego" system, a data-flow path is built by connecting outputs to inputs, directly or through channel objects.

Source note: Object-Oriented Approaches

Multimedia classes (ways to build the hierarchy)Media as classes

  • A media class hierarchy relates the media: Medium → Acoustic medium (music, speech, with Opus, Note, Audio_Block, Sample value), Optical medium (video, Video_Scene, Image, Image_Segment, Pixel, line, column; animation; text), other continuous medium, discrete medium.
  • A class such as Pixel uses multiple inheritance.
  • A special property of all multimedia objects is the continuous change of their internal state during their life span; data transfer lasts as long as the connection is active.
Source note: Object-Oriented Approaches

Multimedia classes (ways to build the hierarchy)Communication-specific metaphors as classes

For distributed environments, classes tied to a communication system. Blakowski defines information, presentation and transport classes: information objects build presentation objects and are converted into transport objects for transmission.

Source note: Object-Oriented Approaches

Object-Oriented ApproachesSimple and compound multimedia objects (BMO, SMO, CMO) (1/2)

Term Meaning
BMO (Basic Multimedia Object) The long data string of an SMO. SG:BMO (segmented): definite length (single image, screen or text record). ST:BMO (streamed): a priori undetermined duration (real-time voice or video)
SMO (Simple Multimedia Object) A BMO with two headers
CMO (Compound Multimedia Object) A combination of SMOs with two headers: orchestration header (temporal relations; the SMOs are individually synchronized and jointly orchestrated) and concatenation header (logical and spatial relations)

Example: an image, a voice annotation and a pointer movement annotating the voice form one CMO.

A CMO can be created and managed by N users at multiple locations. The system must allow users to create SMOs and CMOs, share, store or modify a CMO, preserve temporal, logical and spatial relations at all users at all times, define, manage and monitor the activity, and monitor and restore services after failure or degradation.

Source note: Object-Oriented Approaches
